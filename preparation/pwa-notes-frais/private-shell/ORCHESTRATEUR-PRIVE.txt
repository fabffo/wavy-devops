Contrat du moteur
release-private.py est inactif sans --execute-on-approved-host ; CLI et backend
refusent tout hôte hors wavy-preprod, DOCKER_HOST/DOCKER_CONTEXT ou daemon autre
que unix:///var/run/docker.sock. Dotenv machine canonique : <repo>/.env.preprod.
Profil strict tunnel, origine http://localhost:24443, port loopback 24443.
Aucun Nginx natif, DNS, TLS public ou ouverture 80/443. Les trois binds privés
restent RO ; les quatre images sont celles du release-plan existant.

Le moteur réutilise Operation de scripts/preprod_operation.py : même inode
<repo>/deployments/preprod.lock, flock non bloquant et réservation persistante
preprod-reservation.json, état canonique deployments/pwa-release en 0700.
Pas de nouveau verrou concurrent. Aucun run accepté par simple environnement.
reserve produit le run et le hash du plan profilé private-tunnel-v1 ; il conserve
les requiredChecks du plan HTTPS sans les certifier et sans modifier ce plan.
Les autres actions exigent le run exact et le même hash/sources/dotenv/gate-dir.
Un refus de propriétaire ou de flock ne ferme jamais une autre opération.
Une erreur du propriétaire ferme le socket AVANT de lire les preuves ou appeler
Docker, même si le JSON d'état est corrompu. La réservation reste en place.
closureConfirmed exige ensuite des probes HTTP avec marqueur Nginx, distincts
d'un simple succès d'unlink. En panne Nginx, l'absence de preuve est consignée.

Étapes séparées, aucune activation automatique
reserve -> reserved
prepare : preuve maintenance/schéma/synthétique et précontrôles, quatre images
OCI/platforme, snapshot initial dans l'historique ; barrière sur l'image Shell
actuelle avec fermeture ciblée ; backup initial cinq DB + Contrats/Notes si
présentes ; précontrôles/fermeture refaits après backup ; capacité V3 ; provisionnement ; contrôle RO/subpath ; second backup
complet cinq DB + Contrats ET Notes -> awaiting-restore.
restore : HMAC avant déchiffrement, catalogues et pg_restore réel dans cinq DB
jetables, copie des deux racines, empreintes de chaque fichier et 100:101:0700,
puis nettoyage du seul projet isolé et publication de preuve -> restored.
deploy : revérification preuves/backup/stockage/cohorte, Factures API puis
Factures Front puis PWA puis Shell, --no-deps --no-build --pull never, validation
healthy/Flyway/RepoDigest/ERP, point d'entrée toujours fermé -> prepared.
open-test : autorisation opérateur liée aux IDs/cohorte/backup, contrôles refaits,
une session WAVY_SESSION via pipe hérité -> testing au premier plan, durée <=900 s,
fermeture finale vérifiée -> tested. Aucun enfant ne détient le flock du test.
validate : attestation du parcours réel ET nettoyage client datée après fermeture,
liée au run/backup/IDs ; contrôles ERP et fermé -> validated, toujours fermé.
abandon : fermeture + ERP ; si mutation, validation complète ou rollback complet
obligatoire ; archive durable puis libération de la réservation. Les binds privés
et le blocage des écritures Notes restent en place, aucune ouverture implicite.

Réservation conservée entre toutes ces étapes, après erreur, validate et rollback.
Pas d'enregistrement de promotion publique/HTTPS ni changement des versions actives.
Le snapshot refuse un Shell actuellement publié hors 127.0.0.1:24443, un montage
Shell non revu ou un environnement Shell différent du Compose machine reproductible.
Un Shell existant personnalisé doit donc être réconcilié avant l'opération.
La mise en place initiale de la barrière recrée le Shell : brève interruption ERP.
La sauvegarde quiesce les six backends : prévoir une fenêtre de maintenance,
la disponibilité ERP n'est pas continue pendant la sauvegarde cohérente.

Fermeture et durée
session-gate.py n'accepte plus --authorize-test/--session-cookie-file autonomes.
Le moteur transmet la session uniquement par pipe hérité, jamais argv/env/état/
journal. Le grant est en mémoire, fermé par défaut et au redémarrage ; seule la
session exacte est admise. Deux cookies WAVY_SESSION ou des contrôles CR/LF sont
refusés. Les vérifications UTC/monotone et le timer bornent la durée à 900 s. Le gate
vérifie aussi l’échéance absolue la plus proche des trois preuves (prérequis,
restauration, autorisation), y compris si le démarrage du child est retardé.
PDEATHSIG Linux tue le gate si le parent meurt, avec recontrôle de parent au
fork. Le socket est retiré avant toute commande Docker de fermeture ou rollback.
Un socket absent/service mort => PWA 404, écritures Notes 403 avec marqueur.
La suppression finale du socket par le gate vérifie son inode : aucun nouveau
socket ne peut être effacé par l'ancien processus.
Les probes PWA sont répétées pendant la fenêtre (intervalle 2 s, curl borné) ;
un échec observé retire le socket dans finally, sans commande Docker.
SIGUSR1 au PID ORCHESTRATEUR vérifié demande une fin normale de fenêtre (boucle
200 ms, puis fermeture/probes), sans reload. SIGINT/SIGTERM sont des échecs :
fermeture, phase failed, inspection/reprise explicite. SIGKILL ne peut écrire
l'état final : le gate enfant meurt, la réservation et pending survivent.
Une requête déjà admise/en vol n'est pas annulée. Un hôte suspendu/panne FS ne
constitue pas une preuve de disponibilité ; aucune garantie contre root/Docker.

Notes et ERP
Les lectures ERP de Notes/justificatifs restent contrôlées par Gateway/API.
Toutes les méthodes autres que GET/HEAD sous /api/notes-frais sont verrouillées
pendant fermeture et rollback, y compris transformations et justificatifs.
Pendant le grant, seule la session test peut les écrire : effet à accepter aussi
pour les utilisateurs ERP. Les routes /api/, cinq modules et / sont conservées.
Les chemins API matriciels/encodages résiduels sont rejetés avant proxy, y compris
les doubles encodages ; les recherches en query string ordinaires restent valides.
Ce filtrage de chemin concerne toutes les API : valider les usages ERP inhabituels.
Les probes de fermeture emploient OPTIONS sans corps/cookie et exigent le marqueur
Nginx, pour ne provoquer aucune mutation métier sur un endpoint qui serait ouvert.
Les tests locaux couvrent POST/PUT/PATCH/DELETE/OPTIONS et les mappings Notes.
Aucun contexte tenant/société/utilisateur n'est inventé ou forcé dans le proxy.

Rollback et reprise
rollback conserve le volume et les DB, ferme avant toute action, puis restaure
les quatre digests snapshot. Le Shell restauré reste DÉMARRÉ avec la barrière
privée, jamais --no-start ; ERP/probes vérifiés. Aucun pg_restore actif, suppression
de justificatif, downgrade de migration ou modification de manifeste.
Une preuve rollback-schema-compatible récente est obligatoire ; si les prérequis
ont expiré, fournir une nouvelle preuve --evidence (même run/plan/origine).
Échec partiel => rollback-failed + réservation + gate fermé ; relancer rollback
avec le même run après diagnostic. Aucun abandon d'une mutation partielle.
resume ne réexécute jamais un provisioning ambigu. Il exige une preuve récente
interrupted-effect-inspected, pending exact et resumePhase dans awaiting-restore,
restored, prepared ou tested. Il conserve le snapshot initial et exige le backup
complet ; les phases avancées imposent restore/IDs runtime/ERP. Une interruption
avant le backup complet ne peut pas reprendre à l'aveugle : rollback puis abandon
et nouvelle réservation/préparation, le provisioning idempotent vérifiera le dossier.
Après une reprise, la validation fonctionnelle antérieure est invalidée.

Une interruption de restore peut laisser uniquement des copies et du staging
privé (dumps déchiffrés) sous deployments/pwa-release/restore-private-*. Le projet
et envFile exacts sont consignés dans restore-attempt.json AVANT up. Après arrêt
confirmé du runner, inspecter ce projet, config --format json et isolation, puis
down --volumes DE CE SEUL PROJET avec ce fichier env. Ne jamais utiliser prune,
restore-preprod.sh, rm d'un volume PREPROD, ni effacer une réservation/reçu V3.
Nettoyer le staging privé ciblé après preuve que les copies sont retirées. Le
relecteur doit attester cette inspection avant resume. En cas d’échec ou timeout de down, le staging et envFile restent présents en
0700/0600 ; ils ne sont retirés qu’après down et état cleaned persisté. SIGTERM
ou SIGKILL conservent aussi ces données de reprise. Ne supprimer aucun fichier
avant confirmation du retrait des copies.
