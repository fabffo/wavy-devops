B1 — BLOQUANT : le contrat de consultation après rollback est incomplet
Références : dossier §2 lignes 75–79 et §6 ; ancienne NoteFraisControleur à b277edb ;
nouvelle NoteFraisJustificatifControleur à 09fcd98 ; routes.conf @private_notes_read.
Fait : b277edb expose GET collection, GET /{id}, GET /synthese-mensuelle, avec
contexte tenant/société/utilisateur ; aucun contrôleur justificatif n'est présent
dans l'arbre de cette ancienne révision. Les nouvelles routes GET /{id}/justificatif
et /{id}/justificatif/contenu sont dans le nouveau contrôleur seulement.
Les GET/HEAD passent le gate fermé vers l'API : Nginx n'ajoute pas ces capacités.
Le retour de métadonnées pieceCheminStockage ne restitue pas les octets ndf:<UUID>.
Conséquence : sécurité des originaux et compatibilité SQL ne valent pas continuité
fonctionnelle des pièces. L'affirmation « Notes en lecture seule » doit distinguer
liste/détail/synthèse, rendu de l'ancien Front et téléchargement des nouveaux fichiers.
Action : documenter le contrat de service dégradé après rollback ; le faire accepter
explicitement si le téléchargement est indisponible. Ne jamais réactiver les écritures
anciennes ni exposer le volume pour compenser. Si consultation des pièces obligatoire,
NO GO jusqu'à solution préalablement autorisée et testée, hors de cette revue.
Critère mesurable : sur copie contenant note historique ET note/pièce créées par la
nouvelle API, ancienne API + ancien Front affichent les champs attendus sans mutation ;
GET/listes/synthèses et refus croisés testés. Résultat explicite de chaque GET pièce ;
indisponibilité acceptée ou blocage, jamais 404 compté comme succès de lecture.
Preuves manquantes : scénario ancienne API/ancien Front, statuts, captures synthétiques,
hash des originaux et métadonnées avant/après, acceptation du mode dégradé.

B2 — BLOQUANT : validation JPA/Flyway/logique sans point d'exécution défini
Références : dossier §2 lignes 64–74, §5 ; restore-private.py lignes 154–190.
Fait : helper démarre cinq PG sans réseau, restaure, vérifie tables/documents,
puis down --volumes en finally ; proof publiée uniquement après nettoyage réussi.
Il ne lance aucune API ni validation Flyway/JPA et ne garde pas les copies après succès.
Le dossier exige ces contrôles mais ne fournit ni commande ni protocole approuvé
permettant de les effectuer avant destruction. Les faire après restore est impossible
sur les volumes supprimés. Joindre l'API au réseau PREPROD serait un contournement.
Action : préparer et autoriser un protocole complémentaire isolé avant tout GO.
Définir dépendances, credentials éphémères, profils, réseau isolé sans ressource active,
point de contrôle avant nettoyage, validations anciennes/nouvelles et revue des logs.
Ne pas modifier le helper sans autorisation. Ne pas déclarer son proof JPA-compatible.
Clarifier l'ordre des attestations : isolated-restore-capacity est un dimensionnement
avant prepare ; preuve de restauration du lot de ce run se produit ensuite, avant deploy.
Si rollback-schema-compatible exige préalablement une restauration réelle, identifier
un exercice préalable approuvé ; ne pas attendre du lot créé par prepare qu'il prouve
rétroactivement son propre prérequis. Aucun true anticipé pour débloquer le cycle.
Critère : procédure exécutable approuvée + succès Flyway validate et JPA validate pour
les versions/profils effectivement utilisés, sans migration/repair/DDL non autorisés.
Preuves manquantes : protocole, sorties, topologie/dépendances et ordre exact.

M3 — MAJEUR : matrice d'isolation pertinente mais pas complètement déclinée

Points solides : 2 tenants, 4 sociétés, 4 utilisateurs distincts, pas de supervision,
session autorisée du gate pour les mutations négatives ; aucune donnée personnelle.

par endpoint/méthode : collection/recherche/filtres/synthèse, détail, métadonnées,

expiration/logout/révocation des habilitations durant fenêtre pas opérationnalisés.

requête négative ne change QUE le contexte ou l'ID cible. Cas droits manquants séparés.
Inclure cookies multiples/malformés, société falsifiée/non allouée et lectures après
logout ; ne pas utiliser un ID inexistant comme seule preuve anti-IDOR.
Critère : 100 % cases applicables exécutées ; zéro octet/métadonnée hors périmètre,
zéro mutation après refus ; 401 ou 403/404 selon contrat précis, origine gate/backend
identifiée sans exposer un port supplémentaire.
Preuves manquantes : URLs contractuelles, droits/IDs réels, grille de résultats.
